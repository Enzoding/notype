## target/ 为什么这么大

本项目是 Rust 2021 + GPUI Kit 0.8 + macOS 原生绑定。当前 Cargo.toml 只自定义 release profile，dev/test 使用完整调试信息和默认增量编译；没有发现项目或用户级配置覆盖这些缓存控制项。工具链为 rustc/Cargo 1.95.0，正常依赖树去重后约 444 个包（当前 host 与 normal 依赖口径）。

| 构成 | 文件逻辑大小 |
| --- | ---: |
| debug/deps | 7.45 GB |
| debug/incremental | 1.93 GB |
| debug/build | 221.41 MB |
| debug 根目录可执行文件等 | 209.54 MB |
| release/ 全部构建产物 | 1.72 GB |
| fingerprint 等 | 小量元数据 |

更准确的目录分配统计：`du -sk target` 返回 10,026,412 KiB，即约 **9.56 GiB / 10.27 GB**。扫描发现约 16,713 个重复硬链接条目，解释了逻辑求和较大的主要部分；不同统计口径仍有差异，不能把所有文件大小相加当作删除后的实际释放量。

具体证据：

- debug/deps 中 `.o` 文件约 2.84 GB，`.rlib` 约 2.39 GB，`.rmeta` 约 1.52 GB。
- AppKit 绑定、GPUI、GPUI Component、GPUI Base 都有体积较大的中间库；单个 GPUI rlib 约 179 MB，AppKit rmeta 约 118 MB。
- 同一组件留有多个编译上下文的 hash 产物；check/build/test、profile、feature 等不同配置都可能产生不同缓存，不能把不同 hash 一概认定为无用文件。
- 已改名前缀 `opentypeless` 的对象文件仍约 695 MB，另有旧前缀增量缓存。它们是历史积累的明确迹象。
- `cargo clean --locked --dry-run -p notype` 列出约 3.0 GiB 的本项目产物删除范围，没有实际删除。该范围包括当前有效产物，不是全部陈旧垃圾，也不保证同等物理空间回收。

判断：**体积在这个技术栈下常见且可解释，但当前确实包含历史积累，值得治理。** 它不是用户打开应用时生成的缓存；普通用户安装的应用不会携带整个 target/。相同配置的重复构建会复用缓存，并非每次构建都完整增加一套。但长期改依赖、feature、工具链、profile、包名时，旧产物可能留下。

Cargo 官方目前说明：自动清理覆盖 Cargo home 的全局下载缓存，尚未覆盖项目构建产物，因此不能依赖它给 target/ 自动设上限。[Cargo 配置与全局缓存](https://doc.rust-lang.org/cargo/reference/config.html#global-caches)。

## 推荐的构建空间治理

### 日常调试配置

建议先尝试以下设置，保留本项目的增量编译，减少依赖的调试符号：

```toml
[profile.dev]
debug = "line-tables-only"
incremental = true

[profile.dev.package."*"]
debug = 0
```

应用自身保留回溯行号，依赖不再保留完整调试信息；代价是调试依赖内部变量的能力下降。需要深入 LLDB 调试时再有针对性地打开调试信息。类型元数据仍然需要保留，因此不能预先保证从 10 GB 降到某个固定数值。[Cargo profiles](https://doc.rust-lang.org/cargo/reference/profiles.html#debug)、[依赖覆盖](https://doc.rust-lang.org/cargo/reference/profiles.html#overrides)。

改变 profile 会产生不同编译产物，并不会删除旧产物；第一次切换可能暂时更大。应在无构建任务时配合一次受控清理，然后重新测量冷构建后的稳定基线。以上设置尚未修改或实测。

### 控制长期增长

1. 日常固定一套 dev/test 设置，不频繁改变 RUSTFLAGS、feature 和工具链；release 只在打包时构建。
2. 需要回收空间时优先检查本项目产物，使用 `cargo clean -p notype --dry-run` 预览；定向清理比每次全量清理更能保留依赖编译收益。
3. 工具链、主依赖或构建 profile 大幅变化后安排一次全量清理；避免每次启动应用前清理 target，这会强制反复冷编译。
4. 在开发维护脚本中加入大小检查：以优化后实测基线的 1.5 倍作为预警参考、2 倍作为清理评估参考，每月复查。它们是建议阈值，不是 Cargo 自带的硬上限。
5. 自动清理若要落地，应只管理构建目录，在无构建任务时执行并记录前后大小；不得顺带清理 Application Support 中的数据库、录音、恢复任务或凭据。

不建议单纯把 target 移到另一个目录来当作减容，也不建议一开始就关闭所有增量编译或每次全量清理。当前 release 已配置 LTO、strip 和体积优化；发布可执行文件约 16 MB，不能通过只看最终二进制来估计编译目录大小。

官方清理命令及 dry-run 范围见 [cargo clean](https://doc.rust-lang.org/cargo/commands/cargo-clean.html)。

## 运行数据的长期增长（与构建缓存分开）

0.1.1 的“保存录音”默认开启，当前设置未显式覆盖，且已观察到持续保存 WAV。它们是用户归档，不是可随意删除的缓存；尚无按总空间或天数自动限制。按现有格式，每分钟约 1.92 MB：

| 每日录音量 | 每 30 天 | 每 365 天 |
| --- | ---: | ---: |
| 10 分钟 | 576 MB | 7.01 GB |
| 30 分钟 | 1.73 GB | 21.02 GB |
| 60 分钟 | 3.46 GB | 42.05 GB |

0.2.1 预览新增的恢复缓存目前为空。成功任务归档后清理；失败任务按七天保留，但清理依赖恢复扫描，不是独立定时维护。原始日志使用设备原生采样率的 f32：以 48 kHz 为例，十分钟单声道约 115.2 MB，双声道约 230.4 MB，明显大于最终 19.2 MB 的 WAV。若润色失败并同时保留原始日志和归档 WAV，会出现暂时双份保存。

另外，静态审阅发现 clear_history 先通过 LIMIT 100 的 history() 取音频路径，再删除全部历史行。未来超过 100 条后执行“清空历史”可能留下更旧的录音文件。当前只有 47 条，且未发现孤立 WAV；本轮未触发该操作，也未修改实现。

后续产品存储治理应分别考虑：长期录音的用户可见保留策略与总量预算、恢复日志的格式压缩/归一化与硬容量预算、定时清理触发、孤立文件核对，以及清空历史超过 100 条的回归修复。
